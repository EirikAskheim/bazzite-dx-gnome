Executive summary

The system is usable and has ample disk and memory capacity, normal sampled temperatures, synchronized time, and no recorded Btrfs device I/O or corruption errors. It is nevertheless marked degraded because docker.socket cannot start. The most significant recurring software fault was traced to the third-party Terra rom-properties-localsearch3 extractor plugin rather than GNOME LocalSearch itself. Removal of that plugin has been added to the image recipe. The third-party ASUS user daemon also repeatedly aborts.

No out-of-memory kill, kernel panic, filesystem corruption, or explicit NVMe I/O failure was found in the inspected logs. Direct NVMe SMART access required elevated privileges and could not be completed.

Findings and recommended actions

HIGH · root cause found · image fix prepared

Terra ROM Properties plugin crashes GNOME LocalSearch

/usr/libexec/localsearch-extractor-3 generated 23 of 41 core dumps in the original seven-day sample, including seven during the sampled boot. The crash was reproduced on demand with a Wine DLL:

localsearch extract ~/Games/capybara/wow1/drive_c/windows/syswow64/d3d12.dll
# Extractor subprocess exits on signal 11; instruction pointer is NULL.

The MIME type application/vnd.microsoft.portable-executable selects 14-rp-executables.rule, which loads libextract-rom-properties.so. Both belong to Terra’s rom-properties-localsearch3-2.8-1.fc44, not Fedora’s localsearch-3.11.1-1.fc44. Historical LocalSearch error records also concentrate on formats claimed by this plugin—particularly DLL, EXE, SO and TGA files. LocalSearch’s get_file_metadata() invokes the plugin callback immediately before the null-address fault.

A controlled test masked all nine ROM Properties extraction rules and retried the same DLL. It returned “unknown target graph” without a segfault and created no new core dump. This isolates the failure to the plugin/rules path; updating or resetting the LocalSearch database alone will not fix it.

  • Durable image fix: recipes/recipe.yml now removes rom-properties-localsearch3. Build/deploy the updated image and reboot, then retry the reproduction command. The standalone ROM Properties application and GNOME’s normal extractors are not intentionally removed.
  • Immediate mitigation before deployment: stop indexing with systemctl --user stop localsearch-3.service, or place a .nomedia file at the root of large game/Wine trees such as ~/Games and restart LocalSearch. This trades search coverage for stability.
  • After deployment, restart/reset LocalSearch only if it does not automatically revisit prior failures. Preserve one old dump if filing a Terra or ROM Properties bug.

HIGH · image fix prepared

Docker socket fails because the docker group does not exist

docker.socket is enabled but failed with status=216/GROUP. The docker group remains absent after boot, while other standard groups resolve normally. This is the direct reason systemd reports a degraded state. A stale root-owned /run/docker.sock is present.

  • Fix prepared: files/system/usr/lib/sysusers.d/docker.conf now declares the docker system group in the image. systemd-sysusers will create it during boot after the updated image is deployed.
  • Add intended interactive users to the group separately if they need direct access to /run/docker.sock; group membership grants root-equivalent Docker control.
  • After deployment, confirm with getent group docker and systemctl status docker.socket.

MEDIUM · root cause understood

Homebrew ASUS user daemon is incompatible with this model’s Aura topology

The Homebrew-installed asusd-user 6.3.8 aborts after requesting the legacy D-Bus object /xyz/ljones/Aura. The running system daemon exposes two device-specific lowercase objects under /xyz/ljones/aura/, corresponding to the GZ302EA keyboard’s USB IDs 0b05:18c6 and 0b05:1a30. The user daemon also looks for a nonexistent Default_US.ron layout. Its unchecked D-Bus error causes the Rust process to panic, after which systemd restarts it until the rate limit is reached.

This is consistent with upstream OpenGamingCollective issue #159, filed for this exact GZ302EA model and asusctl 6.3.8. That issue documents duplicate Aura entries, multiple exposed Aura devices, and GUI failure. The correction was merged after the 6.3.8 release. Inspection of Terra’s currently available 6.4.0 RPM shows that its packaged aura_support.ron still contains both problematic GZ302 entries, so that build does not yet provide the merged data fix.

A newer asusctl-6.4.0-1.fc44 RPM is available from Terra, but installing it is not recommended on top of the current Bazzite/Homebrew setup. The RPM includes asusd, asusd-user, and asusctl, but not ROG Control Center. Meanwhile, the active Homebrew system unit in /etc/systemd/system/asusd.service explicitly starts /opt/ublue-asusctl/bin/asusd; it would override the RPM unit in /usr/lib/systemd/system. Installing the RPM would therefore create a mixed 6.4 user/CLI and 6.3.8 system-daemon installation rather than a clean replacement. A Bazzite maintainer has also explicitly advised users not to layer the RPM and to use Universal Blue’s Homebrew casks.

  • Safest immediate resolution: disable asusd-user.service. It is only required for custom per-key effects and AniMe sequences; standard predefined keyboard effects and the system daemon do not require it: systemctl --user disable --now asusd-user.service.
  • Keep the working Homebrew system daemon for normal platform, battery, and predefined Aura controls. Do not add Terra’s asusctl RPM to this image while the Homebrew daemon installation remains.
  • For a future full fix, upgrade both Universal Blue casks together once they publish a post-6.3.8 build containing the GZ302 Aura correction. Do not upgrade only one half of the daemon/client pair.
LOW · understood Atomic/OSTree integration noise

Early account lookups and /boot warnings do not indicate missing accounts or disk damage

Account messages: the audio, disk, kvm, video, render, tss, and similar lookup failures all carry journal field _RUNTIME_SCOPE=initrd. They occur at roughly two seconds, while the small temporary initramfs environment is running—not in the final operating system. Inspection of the active initramfs found no /etc/passwd, /etc/group, /usr/lib/passwd, or /usr/lib/group, so initramfs udev cannot translate those names while initially parsing the host’s udev rules. After the switch to the real root at seven seconds, the account database becomes available and real-root udev reports no equivalent failures.

All checked accounts except the independently missing docker group resolve in the running system. Current device nodes also have their intended ownership: NVMe block devices are root:disk, sound devices are root:audio, /dev/kvm is root:kvm, DRM render nodes are root:render, and TPM nodes use tss. Therefore the second real-root udev pass corrected/applied permissions. This is initramfs packaging noise rather than evidence that the installed account database is broken. Do not duplicate all standard groups in this image to suppress it; a proper upstream fix would make the initramfs carry the static account database.

Non-empty mount points: /boot and /var/home are directories in the immutable root layout before their real filesystems/subvolumes are mounted. systemd emits a generic warning because those mount-point directories contain placeholders. Both mounts then succeed. The separate ext4 /boot filesystem passes fsck as clean, is mounted read/write, and has no recorded ext4 or NVMe I/O errors.

“Remote address changed”: this misleading text is Linux error EREMOTE, not a network error. On this OSTree system /boot/loader is intentionally a symlink to loader.0, allowing deployment boot entries to be switched atomically. systemd-logind’s strict boot-entry reader rejects a symlink in that path, especially on a separate /boot filesystem, and logs the error whenever it refreshes boot-loader information. This exact incompatibility is documented in systemd issue #35293 and tracked as an OSTree Boot Loader Specification integration limitation.

  • No local repair is recommended. Do not replace /boot/loader with a directory; OSTree owns that symlink and changing it can break atomic boot-entry updates.
  • The practical effects are log noise and incomplete bootctl/logind boot-entry enumeration. GRUB booting, the two OSTree entries, rpm-ostree deployments, and the filesystem itself are currently healthy.
  • Reassess only if a future boot fails, device permissions are wrong after startup, rpm-ostree cannot deploy, or fsck/I/O errors appear. Otherwise allow Fedora/Bazzite/systemd/OSTree updates to resolve the integration issues upstream.
MEDIUM · probable common dock/link event

USB-C dock resets interrupt camera, audio, and Ethernet; ACPI and DPCD messages are mostly separate

USB-C/dock evidence: the external devices are behind paired Genesys Logic USB 2.1 and USB 3.1 hub trees, not independent direct connections. The USB 2 path carries the Focusrite Scarlett Solo and input devices; the USB 3 path carries the Logitech StreamCam and Realtek RTL8153 Ethernet. At 09:54 on September 4 and 09:09 on September 5, both top-level hub paths disappeared together, followed immediately by loss of the downstream audio, camera, and Ethernet devices. NetworkManager removed the RTL8153 interface, PipeWire saw Broken pipe/No such device, and GNOME briefly lost a logical monitor. This simultaneous tree-wide removal points to removal/reset of the dock’s upstream USB-C link or power—not simultaneous failure of every peripheral. The journal cannot distinguish an unintended reset from deliberately unplugging the dock; if those times match manual unplugging, this sequence is expected.

USB audio: the large burst of cannot set freq 48000 to ep 0x84, usb_set_interface failed (-19), and StreamCam runtime-rate messages starts only after the StreamCam has disconnected. Error -19 means the device no longer exists. These are teardown/re-enumeration consequences, not evidence that 48 kHz is unsupported. The Scarlett currently runs normally at 48 kHz/S32_LE, advertises multiple rates, and already has runtime power control forced to on. Focusrite also recommends a direct port, supplied/known-good cable, and avoiding a hub when diagnosing USB interface dropouts.

USB power management: the Scarlett and RTL8153 are already power/control=on, while both Genesys hub tiers and StreamCam use auto; tuned is active. Autosuspend is therefore a plausible contributor but is not proven—the complete USB 2 and USB 3 trees can also vanish because the cable/dock loses power or the Type-C link retrains. The occasional UCSI GET_CURRENT_CAM and Alt mode has timed out messages are consistent with Type-C alternate-mode negotiation around dock attachment. They are not persistent during normal operation.

DisplayPort, not DisplayLink: no DisplayLink/Synaptics USB graphics adapter or DisplayLink driver was found. The external 3440×1440 display is exposed by AMD DRM as native DP-1, consistent with DisplayPort Alt Mode over USB-C. The repeated DPCD read addr.0x378 message comes specifically from AMD’s handle_hpd_irq_replay_sink path. Address 0x378 belongs to the DisplayPort Panel Replay status range, so this more strongly implicates a Panel Replay/HPD exchange—probably the internal eDP-1 panel—than the external dock. The log line alone does not identify the connector, so correlate it with actual internal-panel flicker or resume failure before treating it as actionable. It is not evidence of DisplayLink failure.

ACPI: each boot reports duplicate namespace objects \\_SB.CIND and \\_SB.PCI0.GPP4._S0W/_PR0/_PR3 with AE_ALREADY_EXISTS. These tables are supplied by firmware; Linux rejects the duplicate definitions and continues. USB4 ownership is subsequently granted to the OS, both displays work, and no ACPI-related suspend failure was established. Treat these as low-severity BIOS table defects unless a repeatable GPP4 device power/resume problem appears.

Recommended isolation order

  1. Highest-value test: connect the Scarlett directly to the computer and put the StreamCam on a different physical USB-C port (or leave it disconnected), while using a known-good short USB-C cable for the dock. If the resets stop, the software audio-rate messages need no separate fix.
  2. Separate video from the hub: test the monitor with a direct USB-C-to-DisplayPort cable, then test the dock without the monitor. Also try the other USB-C port and temporarily reduce the external display refresh rate. This distinguishes DP signal-integrity/Alt-Mode load from the dock’s USB hub path.
  3. Test power management temporarily, not yet as an image change: while the current topology is attached, set power/control to on for the two Genesys hub tiers and StreamCam. Revert by reconnecting/rebooting. If this alone prevents reproducible idle/resume drops, add a narrowly matched udev rule later; do not disable USB autosuspend globally.
  4. Firmware: system BIOS GZ302EA.314 is the current ASUS release and fwupd reports no available update. ASUS separately publishes a recommended ROG PD Firmware Update Tool (2.13.0.001), currently Windows-only; verify/apply it from Windows if its installed state is unknown. Check the dock and monitor vendors for firmware too.
  5. If still reproducible: record the exact disconnect time and whether charging, DP, Ethernet, camera, and Scarlett all drop. Capture journalctl -k -b --since "2 minutes ago", test one known-good cable, and report it to Bazzite/AMD with the dock model and topology. For an internal-panel symptom, report the 0x378 Panel Replay line separately from the USB reset.

LOW · noisy configuration

Battery threshold udev rules target unsupported attributes

udev repeatedly attempted to chmod several absent battery threshold files. This hardware currently exposes only charge_control_end_threshold, which is writable and read as 100 at inspection time. The custom charge-limit-80.service reported success, but the sampled value was 100, so the intended 80% limit should be verified independently.

  • Condition udev actions on attribute existence and avoid world-writable (0666) sysfs permissions where a narrower mechanism can be used.
  • Verify whether asusd later resets the threshold and whether the charge-limit service truly persists 80%.
LOW · SELinux policy noise

SELinux denials during boot/greenboot checks

SELinux is enforcing. Boot update tools generated permissive-domain denials while reading proc/userdb, while greenboot test chcon operations were blocked in enforcing mode using an intentionally invalid test label. Greenboot subsequently reported the kernel boot successful, so no direct boot failure was observed.

  • Update the relevant bootc/bootupd/greenboot policy packages with the image.
  • Do not blindly install a broad audit2allow policy for these events; first confirm the operation is legitimate and still fails on an updated image.

Scope and limitations

Reviewed system and kernel journals for the current boot, the previous boot at a summary level, failed system/user units, seven-day coredump records, disk and Btrfs status, memory, temperatures, SELinux denials, time synchronization, boot/deployment state, and selected service logs.
