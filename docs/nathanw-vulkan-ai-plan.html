1Verdict: why Nathanw, not Halogen

The source post A/B-tested both stacks on the same 128 GB Strix Halo box (8k / 32k / 55k bands × agentic/code, thinking on, 3 repeats). Halogen wins cold prefill (~758 vs ~362 tok/s @ 55k agentic), but Nathanw wins the metric agents actually live on — warm decode at depth (47 vs 39 tok/s @ 55k agentic; 119 vs 35 tok/s @ 55k code via MTP speculative decoding). Halogen is also operationally exclusive: own .hgn weight tree (~121 GiB), owns the GPU, no concurrent embedding models, ~7 min cold load, SSE streaming wedged at 32k+.

Decision for this repo: implement the Nathanw production configuration. Do not adopt Halogen except as a future optional batch-ingest path on a dedicated box.

3How it maps onto this Bazzite repo

Already present — reuse as-is
  • files/system/etc/modprobe.d/amdgpu_llm_optimized.conf (gttsize, ttm pages_limit/pool)
  • files/system/etc/udev/rules.d/99-amd-kfd.rules (kfd/drm → render)
  • files/justfiles/llm-gpu.just → ujust llm-gpu-setup (groups, dracut, udev)
  • uv, ROCm/Vulkan userspace via Bazzite base + ollama.service env pattern (AMD_VULKAN_ICD=RADV, VK_ICD_FILENAMES=…radeon_icd…)
New — proposed repo additions
  • files/justfiles/nathanw.just — nathanw-install, nathanw-models-download, nathanw-run, nathanw-verify
  • files/system/usr/lib/systemd/user/llama-swap.service (preferred: user scope so it sees $HOME models + /dev/dri via render group)
  • Optional bake: files/system/usr/lib/sysusers.d/nathanw.conf + tmpfiles.d/nathanw.conf + system/nathanw-llama-swap.service + preset, mirroring ollama.conf/openviking.conf
  • docs/nathanw-vulkan-ai-plan.html (this file)
Scope choice: run llama-swap as a systemd user service (like the author), not a system service. A system user (ollama-style) would need the ~96 GiB model tree readable under /var/lib and GPU group membership; that is Phase 2 if boot-time preload is ever wanted. Phase 1 needs zero image rebuild — only a new justfile + user units.

4Implementation phases

Phase 0 — prerequisites (today, no code)

  • Confirm Strix Halo + ≥96 GiB free for weights (this machine reports ~111 GiB available — fits, but tight alongside Ollama models).
  • Run ujust llm-gpu-setup; systemctl reboot if not already done. Keep amd_iommu=pt (NPU requirement); do not switch to off for Halogen-style prefill gains.
  • systemctl stop ollama before large-model runs — the 125B MoE + 51B n-gram table wants the host mostly to itself.

Phase 1 — user-space install (recommended; no rebuild)

  • Add files/justfiles/nathanw.just: download + verify Nathanw portable tarball (pin v0.7.5, checksum), hf download the 3 model files, install llama-swap binary, write ~/llama-swap/llama-swap.config.yaml + template, install user systemd unit, systemctl --user enable --now llama-swap.
  • Add LiteLLM compose entry mapping local/Qwen3.8-Flash-Next → openai/qwen38-flash-next at http://host.docker.internal:8080/v1.
  • Validate with the verification checklist.

Phase 2 — optional image bake (later)

  • Only if Phase 1 proves stable: add a recipes/recipe.yml script step extracting the portable tarball to /usr/lib/nathanw/ + symlink /usr/bin/llama-server-nathanw, ship llama-swap binary, add sysusers/tmpfiles/preset exactly like ollama/openviking. Weights still stay out of the image.
  • Consider an amdgpu-perf-high-equivalent (force power_dpm_force_performance_level=high) only after measuring a 600 MHz stuck-clock symptom; the infra post cites 27→33 tok/s class effects.

5Runtime wiring

5.1 Standalone llama-server (author's production command, Bazzite paths)

NATHANW=~/.local/share/nathanw/v0.7.5/llama-server
MODELS=/var/lib/nathanw/models/Qwen3.8-Flash-Next
SWAP=~/.config/llama-swap

"$NATHANW" \
  --host 127.0.0.1 --port 8080 \
  -m "$MODELS/AD-4.27bpw/Qwen3.8-Flash-Next-AD-4.27bpw-Q4_K_M-M64-00001-of-00033.gguf" \
  -md "$MODELS/mtp-Qwen3.8-Flash-Next-shared-Q8_0.gguf" \
  --mmproj "$MODELS/mmproj-Qwen3.8-Flash-Next-F16.gguf" \
  --image-min-tokens 1024 \
  -fa on -ngl 999 -b 8192 -ub 2048 -t 4 -fit off \
  --ctx-size 262144 \
  --cache-type-k q8_0 --cache-type-v q8_0 \
  --cache-reuse 1 \
  --spec-type draft-mtp,ngram-mod --spec-draft-n-max 6 --spec-draft-p-min 0.75 \
  --load-mode mmap --no-host --no-repack --tensor-read-lazy on \
  -ot per_layer_token_embd.weight=CPU --n-cpu-moe 0 --parallel 1 \
  --slot-save-path "$SWAP/slots" \
  --jinja --chat-template-file "$SWAP/templates/chat_template.jinja" \
  --reasoning-format deepseek --reasoning-budget 8192 \
  --reasoning-budget-message "Let me provide my answer now." \
  --temp 1.0 --top-p 0.95 --top-k 20 --min-p 0.0 \
  --presence-penalty 0.0 --repeat-penalty 1.0 \
  --chat-template-kwargs '{"preserve_thinking":true}'
Mandatory, non-obvious flags: -fit off + --load-mode mmap + --tensor-read-lazy on (Flash Next's 51B n-gram table requires mmap — never --no-mmap here, unlike generic Strix Halo tuning). Sampling must stay at Qwen official thinking-mode values (temp 1.0 / top-p 0.95 / top-k 20).

6Storage, memory & kernel notes

  • Disk: ~97 GiB total (93 + 2.6 + ~1). Ensure the target filesystem has ≥120 GiB free. Exclude the model tree from restic (/etc/restic/excludes pattern) — weights are re-downloadable.
  • RAM: unified 128 GB; author sees ~44 GiB MemAvailable with Nathanw resident vs ~72 GiB accounting under Halogen — same box, different accounting. Stop ollama/embeddings before benchmarking.
  • Kernel: keep amd_iommu=pt. off buys ~13–16% Halogen prefill but breaks NPU. Check with cat /proc/cmdline.
  • Slot saves: v0.7.4 slot files do not restore into v0.7.5 (indexer V shape changed) — expect one re-prefill, then fine.
  • Future fix to watch: ggml-org/llama.cpp#28136 (lazy PLE direct reads, 2–3× prefill on diverse prompts) — the path to Halogen-like first-fill without leaving llama-swap.
